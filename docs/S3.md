# S3

`./src/shards3/internal/modules/s3`

The S3 module implements a **virtual-hosted-style** S3-compatible API for ShardS3. It handles all HTTP request routing, parameter parsing, signature validation, and XML response serialization.

## Architecture

The S3 server is designed with a custom request/response pattern that uses Go struct tags to define how HTTP parameters are parsed and responses are formatted:

- **Server** (`web/server.go`): HTTP entry point using Go's `net/http` and `chi` router
- **Middleware** (`web/middleware.go`): SigV4 authentication and request logging
- **Route Handlers** (`web/routeHandler.go`): Virtual host detection and request dispatching
- **Operation Handlers** (`web/handlers_*.go`): Individual S3 operation implementations
- **Services** (subpackages): Authentication, bucket management, object operations

## Virtual-Hosted-Style Routing

The S3 API uses AWS's virtual-hosted-style addressing:
- **Root host** (e.g., `s3.example.com`): Bucket listing operations
- **Bucket hosts** (e.g., `mybucket.s3.example.com`): Bucket and object operations

Routing is determined by:
1. Hostname parsing via `hostrouter` to differentiate root vs. bucket hosts
2. HTTP method detection (GET, PUT, POST, DELETE, HEAD)
3. Query parameter checking to identify specific sub-operations (e.g., `?uploadId=`, `?acl=`)

The `hasKey()` function checks whether the request targets an object (`/path/to/object`) or the bucket root (`/`).

## Request & Response Pattern: Struct Tags

ShardS3 uses an **unconventional but elegant pattern** where HTTP metadata is encoded in Go struct field tags. This enables compile-time, reflection-free parsing.

### Request Parsing: `http` and `range` Tags

Every S3 request struct (e.g., `ObjectRequest`, `BucketRequest`, `MultipartRequest`) uses two tags per field:

```go
type ObjectRequest struct {
    BucketName string `http:"Bucket,host" name:"bucket name"`
    Key        string `http:"Key,path" name:"object key"`
    PartNumber int    `http:"part-number,query" range:"1,10000"`
    Range      string `http:"range,header"`
    IfMatch    string `http:"If-Match,header"`
    MaxKeys    int    `http:"max-keys,query" range:"1,1000" default:"1000"`
}
```

**Tag breakdown:**
- `http:"<name>,<type>"`: Where `<type>` is one of:
  - `host`: Extract from hostname using `bucketFromHost()`
  - `path`: Extract from URL path
  - `query`: Extract from query parameter
  - `header`: Extract from HTTP header
- `range:"<min>,<max>"` (optional): Validates integer fields are within bounds; returns `http.StatusBadRequest` if violated
- `default:"<value>"` (optional): Default value if the field is missing
- `name:"..."` (optional): Human-readable field name for error messages

**Parsing flow:**
1. `GetRequest[T]()` uses reflection to enumerate struct fields
2. For each field with an `http` tag, it extracts the value from the specified source
3. Values are converted to the correct type (string, int, time.Time)
4. `HandleRequest[T]()` then validates required fields and checks ranges

### Response Writing: Response Structs with `http` Tags

Response structs use the same tag pattern to automatically serialize fields into HTTP headers:

```go
type ObjectResponse struct {
    LastModified   time.Time `http:"last-modified"`
    ContentLength  int64     `http:"Content-Length"`
    ETag           uint64    `http:"ETag"`
    CacheControl   string    `http:"Cache-Control"`
    ContentType    string    `http:"Content-Type"`
    StorageClass   string    `http:"x-amz-storage-class"`
}
```

The `WriteResponse()` function:
1. Calls `applyHeaders()` which iterates over response struct fields
2. Each field with an `http` tag is written to the response header
3. Time fields are automatically formatted as RFC1123
4. Numeric and boolean fields are converted to strings
5. XML body (if any) is serialized with the S3 namespace and sent after headers

**Example flow:**
```go
WriteResponse(w, http.StatusOK, &responseHeaders, xmlBodyStruct, nil)
// Calls applyHeaders() → sets all header fields → sets status → writes XML
```

## Implemented S3 Operations

### Bucket Operations

**Listing & Metadata:**
- `ListBuckets` — List all buckets with creation dates and continuation tokens (pagination)
- `HeadBucket` — Check bucket existence and get bucket ARN/region
- `GetBucketLocation` — Get configured region for a bucket

**Bucket Configuration:**
- `GetBucketEncryption` — Return encryption configuration (SSE-AES256 by default)
- `GetBucketAcl` — Return Access Control List (full access to owner)
- `GetBucketTagging` — Return bucket tags (currently returns empty tags)

### Object Operations

**Basic Operations:**
- `PutObject` — Upload an object with chunking and sharding
- `GetObject` — Download an object with range request support
- `HeadObject` — Get object metadata without downloading
- `DeleteObject` — Delete a single object
- `DeleteObjects` — Batch delete multiple objects

**Listing:**
- `ListObjectsV2` — List objects in a bucket with prefix/delimiter support and pagination

**Object Metadata:**
- `GetObjectAcl` — Return object ACL (full access to owner)
- `GetObjectTagging` — Return object tags

**Conditional Requests:**
- `If-Match`: Match ETag before retrieval/deletion
- `If-Modified-Since` / `If-Unmodified-Since`: Match object modification time
- `If-None-Match`: Return 304 if ETag matches
- `x-amz-if-match-size`: Match object size
- `x-amz-if-match-initiated-time`: Match multipart upload initiation time

### Multipart Upload Operations

- `CreateMultipartUpload` — Initiate a multipart upload, return upload ID
- `UploadPart` — Upload a single part (indexed 1–10000)
- `CompleteMultipartUpload` — Finalize upload and assemble parts into object
- `AbortMultipartUpload` — Cancel an in-progress multipart upload
- `ListMultipartUploads` — List ongoing multipart uploads in a bucket
- `ListParts` — List parts already uploaded for a given upload ID

## Not Implemented

- **Bucket versioning** (`?versioning`) — No version IDs returned; objects have immutable lifecycle
- **Object metadata headers** (`x-amz-meta-*`) — Not parsed or persisted
- **PUT bucket operations** (CreateBucket, DeleteBucket) — Routing handlers exist but return internal errors
- **Access control refinements** — All users treated as the same "account owner"; no IAM/policy support
- **Object restoration** (`?restore`) — No Glacier-like archival support
- **Bucket policies** (`?policy`) — Not implemented
- **Website hosting** (`?website`) — Not implemented
- **Request/Billing analytics** (`?analytics`, `?metrics`) — Not tracked
- **Replication** — No cross-bucket or cross-region replication
- **CORS configuration** (`?cors`) — Not implemented
- **Bucket notifications** (`?notification`) — Not implemented
- **Object legal hold** (`?legal-hold`) — Not implemented
- **Object retention** (`?retention`) — Not implemented

## Authentication

All requests are verified using **SigV4** (AWS Signature Version 4) via `auth.Service`:

- Validates `Authorization` header format (`AWS4-HMAC-SHA256 Credential=...`)
- Computes request signature using the request's canonical form (method, path, headers, body)
- Compares computed signature with client-provided signature
- Allows configurable time skew (default 5 minutes) to tolerate clock drift
- Returns `403 Forbidden` for invalid signatures or `401 Unauthorized` for missing auth headers

## Error Handling

All S3 errors are returned as XML with status codes:

```xml
<Error>
  <Code>NoSuchBucket</Code>
  <Message>bucket not found</Message>
  <Resource>/mybucket</Resource>
  <RequestId>shards3-request</RequestId>
</Error>
```

Common error codes:
- `NoSuchBucket` → 404
- `InvalidRequest` → 400
- `AccessDenied` → 403
- `InternalError` → 500
- `SignatureDoesNotMatch` → 403

## Default Values

Configured via `config.Cfg`:
- **S3 Region**: Default region name for `GetBucketLocation`
- **Encryption Method**: Default SSE algorithm (e.g., `AES256`)
- **Storage Class**: Default storage class for objects
- **Account ID**: Owner ID returned in ACL/ownership responses
- **Service Name**: Display name for the owner
